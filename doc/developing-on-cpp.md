# Правила разработки кода в команде

## 0. Используемые определения
- 0.1 Модуль - часть программы, характеризующаяся обеспечением завершенного
функционала; может выполняться в одном или нескольких потоках
> Пример: нода, обеспечивающая работу мачты, имеет обособленный завершенный
> функционал по физическому управлению мачтой

## 1. Правила по работе с памятью

- 1.1 Статические данные минимизируем и стараемся использовать поля
классов
- 1.2 Аллокации избегаем

## 2. Правила как планировать отказы в программе и как их обрабатывать

- 2.1 Разрешаем Exception на всех старших микроконтроллерах и
платформах с MMU

```
Исключения в современном С++ полезны по следующим причинам:
* Исключение заставляет обработать ошибку и завершиться/перезапуститься правильно, иначе программа 
будет завершена;
* При возврате в обработчик исключения - уничтожаются все локальные объекты скоупа, что соответствует
правилам работы с ресурсами и RAII;
* Дает возможность провести четкую грань между кодом функционала программы и кодом обработки ошибки.
```

```cpp
#include <stdexcept>
#include <limits>
#include <iostream>

using namespace std;

void MyFunc(int c) {
    if (c > numeric_limits<char>::max()) {
        throw invalid_argument("MyFunc argument too large.");
    }
    //...
}

int main() {
    try {
        MyFunc(256); //cause an exception to throw
    } catch (invalid_argument& e) {
        cerr << e.what() << endl;
        return -1;
    }
    //...
    return 0;
}

```

- 2.2 На младших микроконтроллерах (stm32f303 / stm32f103) мы бережем
место и производительность - исключения запрещены, используем
std::optional или прямой возврат ошибки

```cpp
std::optional<std::string> TryParse(Input input) {
    if (input.valid()) {
        return input.asString();
    }
    return std::nullopt;
}

```

```cpp
enum class EAllocState { NotAllocatedPTR, NoError };
EAllocState Deallocate(ConstPointer ptr) {
    if (ptr == TTreeFields::MemoryAddress) {
        TTreeFields::MemoryAllocated = false;
        return EAllocState::NoError;
    }
    return EAllocState::NotAllocatedPTR;
}

```

- 2.3 В случае с конструкторами - заменяем фабрикой с возвратом
ошибки, внутри выставляем флаги
- 2.4 Весь код, что используется на обоих типах платформ (будем
стремиться, чтобы он весь лежал в папке libraries) - должен поддерживать
вариант с std::exception и вариант с std::optional

## 3. Правила как вести логгирование в коде

- 3.1 При **ревью** кода проверяется наличие двух уровней
логирования WARNING & ERROR & CRITICAL.
- 3.2 Другие уровни логирования можно использовать по мере
необходимости

Уровни логов:

| Уровень лога | Когда использовать |
| --- | --- |
| Trace | Трассировка стека (Stack trace) |
| Debug | Пользовательские события |
| Info | Понятные правильные события |
| Warning | Понятные неправильные события |
| Error | Ошибки, при которых модуль может восстановиться |
| Critical | Ошибки, при которых модуль выключился |

Включенные режимы по умолчанию:

| Release Build | Debug Build |
| --- | --- |
| **Embedded** |  |
| Runtime: Info | Runtime: Info |
| Compile: Info | Compile: Debug |
| **Host** |  |
| Runtime: Info | Runtime: Info |
| Compile: Info | Compile: Trace |

*Это означает, что debug сборка на embedded будет иметь уровень логирования
по умолчанию Info, а также возможность понижения уровня до Debug; Trace сообщения
скомпилированы не будут*

- 3.3 Перед возвратом ошибки функцией или методом, или при
выбрасывании исключения, **необходимо** добавить в лог
**ошибки** сообщение с ее понятным описанием и значениями
ключевых переменных/полей, если они не включены в описание
генерируемого исключения

- 3.4 Для кода, который не запускается на **embedded**
платформе, можно использовать оба формата логирования — и stream, и
printf string.

- 3.5 Для кода, который запускается на **embedded**
платформе, **желательно** использовать stream.

```cpp
auto inst = NYmrlog::TLog<TLock, TSink>{"Internal component"};
auto some_function(int parameter) {
    if (some_error_check) {
        inst << NYmrlog::Error << "Data 1 " << "Data 2 iteration:" << i << NYmrlog::Endl;
        return error;
    }
    if (some_other_error_check) {
        inst.Format(NYmrlog::Crit, "data %s iteration: %d", "Data 1", i);
        exit(1);
    }
    if (some_parameter_check) {
        inst.Format(NYmrlog::Warn,"data %s iteration: %d", "Data 1", i);
    }
}
```

- 3.6 Соответственно, если переменная/поле/параметр выходят за рамки
предполагаемых значений или результат операции вышел подозрительный:
**необходимо** добавить в лог
**предупреждение** сообщение с ее понятным описанием и
значениями этих переменных/полей/параметров
- 3.7 Каждое сообщение об ошибке должно относиться к своему модулю, с
уникальным именем.
- 3.8 Значения, которые мы по каким-то причинам хотим померить -
помечаем тегом **[MEASUREMENT]**

```cpp
constexpr auto CFunc = []() {
    constexpr float CValue{0.56f};
    auto value = CValue;
    auto inst = NYmrlog::TLog{"Internal component", LOG_LEVEL_TRACE};
    for (int i{}; i < CIterations; i++) {
        value *= value;
        inst << NYmrlog::Debug << "processing value = " << result << NYmrlog::Endl;
    }
    return value;
};
// Measure the processing time
auto result = Measure<CFunc>();
auto inst = NComponents::NLogger{"Module B", LOG_LEVEL_DEBUG};
inst << NYmrlog::Debug << "[MEASUREMENT] CFunc() takes " << result << result.count() << " ms" << std::endl;
```

- 3.9 Ошибки рассматриваются относительно модуля, в котором они генерируются
- 3.10 Правила регламинтируют написани логов в пользовательском коде, часть правил
может не применяться при использовании логов в системном коде - драйверах, ядре

> П. 3.10 позволяет отходить от правил #4 и #5 при использовании syslog() в качестве
> инструмента логирования

## 4. Поведение при ERROR
- 4.1 Ошибка выводится в случаях, когда нормальная работа программы нарушена, но потенциально
работа может быть восстановлена
- 4.2 Если ошибка возникает больше разумного для восстановления количества раз, то модуль прекращает
вывод сообщения об ошибке; генерирует ошибку уровня CRITICAL
- 4.3 Модуль может продолжать попытки восстановления без вывода ошибок
- 4.3 Выполнение остальных модулей продолжается
- 4.4 Если восстановление удалось, то модуль продолжает работу

## 5. Поведение при CRITICAL
- 5.1 Критическая ошибка означает, что дальнейшая работа модуля без
вмешательства невозможна
- 5.2 При ее возниковении другие модули **продолжают** работу
- 5.2 Модуль может продолжать попытки восстановления работы,
но при этом не генерируя ошибки уровня ERROR и CRITICAL


> Пример:
> 1. Нода работы с колесом по can не смогла отправить пакет, сопроводив неудачу сообщением уровня WARN
> 2. Если не удалось отправить пакет 10 раз подряд, то выводится ошибка
> 3. Нода пытается переинициализировать драйвер колеса по can и продолжить работу
> 4. Если ситуация повторяется 5 раз подряд, то модуль генерирует сообщения уровня CRITICAL
> и больше сообщения не поступают
> 5. Нода продолжает восстановление общения с драйвером колеса в фоне
> **error** - поскольу невозможно отправить сообщение даже с 10 попытки;
> переиницализация - попытка восстановления
> **critical** - поскольку переинициализация не дала результата, требуется вмешательство,
> но поскольку critical рассматривавется относительно модуля, то остальная работа системы
> не нарушается, и система продолжает работу
